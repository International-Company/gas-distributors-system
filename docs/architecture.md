# البنية والقرارات التقنية

## نظرة عامة

```
src/
  app/                 صفحات Next.js وواجهات API
    (app)/admin/...    صفحات مديري النظام
    (app)/d            صفحات الموزّع
    (app)/account      حسابي (كلمة المرور، PIN، الأجهزة)
    api/v1/...         واجهات JSON (موثقة في docs/api.md)
  server/              منطق الخادم فقط (لا يُستورد في المتصفح)
    db.ts              الاتصال وسياقات العزل withTenant / withSystem
    actor.ts           هوية المنفذ والتحقق من الصلاحيات
    permissions.ts     صلاحيات مديري النظام
    audit.ts           كتابة سجل التدقيق
    auth/              كلمات المرور، الجلسات، PIN
    services/          خدمات الأعمال (الموزّعون، المديرون، الإعدادات، السجلات، التصدير)
    http/              حراس الصفحات وAPI، معالجة الأخطاء، CSRF
  components/          مكونات الواجهة
  lib/                 أدوات مشتركة (تنسيق التواريخ، القائمة)
prisma/
  schema.prisma        مخطط البيانات
  migrations/          ترحيلات SQL (منها ترحيل الحماية: RLS والـ triggers)
scripts/               سكربتات التشغيل والإعداد
tests/                 اختبارات الوحدات والتكامل
```

**القاعدة:** كل عملية تمر عبر خدمة في `src/server/services`، تستقبل `Actor` الذي بناه الخادم من الجلسة، وتتحقق من الصلاحية بنفسها. واجهات API والصفحات طبقة رقيقة فوق الخدمات. لا تُبنى الهوية أبدًا من بيانات يرسلها العميل.

## عزل بيانات الموزّعين (طبقتان)

1. **طبقة التطبيق:** خدمات الموزّع تستخدم `withTenant(actor.distributorId, ...)`، وخدمات الإدارة تتحقق من دور المدير وصلاحيته قبل استخدام `withSystem`.
2. **طبقة قاعدة البيانات (Row-Level Security):**
   - التطبيق يتصل بالدور `gas_app` (ليس مالك الجداول ولا يملك `BYPASSRLS`)، فتُطبق عليه سياسات RLS دائمًا.
   - كل معاملة تحدد سياقها بـ `set_config(..., true)` (محلي للمعاملة فقط):
     - `app.distributor_id`: سياق موزّع واحد.
     - `app.bypass_rls = on`: السياق المركزي (المديرون، المصادقة).
   - **فشل مغلق:** أي استعلام خارج السياقين لا يرى أي صف من الجداول المعزولة.
   - الجداول المعزولة حاليًا: `distributors` و `users` و `audit_logs`. كل جدول بيانات تشغيلية في المراحل القادمة (كشوف، مواطنون، دورات، عمليات، مخزون، مالية) سيحمل `distributorId` وسياسة RLS نفسها.

اختبارات `tests/integration/isolation.test.ts` تتحقق من ذلك على قاعدة PostgreSQL حقيقية.

## المصادقة والجلسات

- كلمات المرور وPIN مجزأة بـ **Argon2id** (معاملات OWASP: 19 MiB، تكراران).
- الجلسة رمز عشوائي (256 بت) في ملف تعريف ارتباط `HttpOnly` و `SameSite=Lax` و `Secure` في الإنتاج. قاعدة البيانات تخزن **تجزئة SHA-256** للرمز فقط.
- يُتحقق من كل طلب على الخادم: الإبطال، مهلة عدم النشاط (من الإعدادات)، العمر الأقصى (7 أيام)، حالة المستخدم، حالة الموزّع وصلاحيته.
- **قفل الحساب** بعد عدد المحاولات الفاشلة المحدد في الإعدادات، مع حد إضافي للمحاولات الفاشلة من عنوان IP واحد (50 خلال 15 دقيقة).
- رسالة الفشل موحدة لكلمة مرور خاطئة ولمستخدم غير موجود، مع تحقق وهمي بزمن مماثل حتى لا يُكشف وجود الحساب.
- كل محاولة دخول (ناجحة أو فاشلة) تُسجل مع الوقت وعنوان IP في `login_attempts` (للإضافة فقط).
- **PIN:** مرتبط بجهاز واحد عبر رمز جهاز في ملف تعريف ارتباط `HttpOnly` و `SameSite=Strict`. تفعيله يتطلب كلمة المرور، ويُلغى بعد 5 محاولات خاطئة. جلسة PIN **لا تكفي للعمليات الحساسة**.
- **العمليات الحساسة** (إعادة تعيين كلمات المرور، إدارة المديرين، الخروج من كل الأجهزة) تتطلب تحققًا بكلمة المرور خلال آخر 15 دقيقة. الواجهة تطلبه تلقائيًا ثم تعيد المحاولة.
- **نسيان كلمة المرور:** يعيد المدير تعيينها بعد التحقق من الهوية، مع إلزام بتسجيل السبب وطريقة التحقق، وإلزام الموزّع بتغييرها عند الدخول، وإبطال الجلسات وPIN افتراضيًا.
- **CSRF:** كل طلب معدِّل يجب أن يحمل `Origin` مطابقًا للمضيف، إضافة إلى `SameSite`.

## دورة حياة حساب الموزّع

| الحالة | الدخول | ملاحظات |
|---|---|---|
| نشط `ACTIVE` | مسموح | قد يكون تجريبيًا أو فعليًا، بتاريخ انتهاء أو بلا مدة |
| معلّق `SUSPENDED/MANUAL` | ممنوع | قرار إداري مع سبب |
| منتهي `SUSPENDED/EXPIRED` | ممنوع | تعليق تلقائي عند انتهاء الصلاحية |
| مؤرشف `ARCHIVED` | ممنوع | مخفي من القائمة الافتراضية؛ لا تُحذف أي بيانات |

**التعليق التلقائي:** يُنفذ عند كل تحقق من جلسة، وعند كل محاولة دخول، وعند عرض قوائم الإدارة. لا يمكن لحساب منتهٍ تنفيذ أي عملية حتى دون مهمة مجدولة. التحديث شرطي (`WHERE status = 'ACTIVE'`) فلا يتكرر السجل عند تزامن طلبين.

التعليق والأرشفة يبطلان كل جلسات الموزّع فورًا.

## سجل التدقيق

- يُكتب **داخل المعاملة نفسها** مع العملية، فلا تُعتمد عملية دون سجلها.
- يحفظ القيم القبلية والبعدية والسبب والمنفذ وعنوان IP. يحذف تلقائيًا أي حقل سري (`passwordHash` و `pinHash` وغيرهما).
- **محمي من التعديل** على مستويين:
  - `gas_app` لا يملك صلاحيات `UPDATE` و `DELETE` و `TRUNCATE` على الجدول.
  - Triggers تمنع التعديل والحذف والتفريغ حتى لمالك قاعدة البيانات.
- المبدأ نفسه مطبق على `login_attempts` و `error_logs`.

## الأخطاء التقنية

كل خطأ غير متوقع في API يُسجل في `error_logs` (الرسالة، المسار، المستخدم)، ويرجع للعميل رسالة عامة دون تفاصيل داخلية. الإشعار الداخلي لمدير النظام عند الأخطاء المهمة يُضاف مع نظام الإشعارات (المرحلة 7).

## القرارات التقنية والافتراضات

| القرار | السبب |
|---|---|
| Prisma مع ترحيلات `migrate` (لا `db push`) | تاريخ تغييرات قابل للمراجعة، ولا حذف بيانات صامت في الإنتاج |
| RLS في PostgreSQL مع دور تطبيق منفصل | عزل لا يعتمد على تذكّر كل مطور إضافة شرط الموزّع |
| جلسات في قاعدة البيانات بدل JWT | إمكانية الإبطال الفوري (تعليق، خروج من كل الأجهزة، مهلة عدم النشاط) |
| واجهات `/api/v1` بدل Server Actions | API موثقة قابلة للتوسع، وأساس للمزامنة دون اتصال (المرحلة 6) |
| التواريخ بتوقيت `Asia/Gaza` وبصيغة يوم/شهر/سنة بأرقام لاتينية | وضوح التواريخ داخل نص عربي |
| إعدادات العملة لا تغيّر العمليات السابقة | كل عملية مالية (المرحلة 4) ستخزن عملتها وقيمتها وقت التنفيذ |
| إعادة الحساب من الأرشيف تعيده «معلّقًا» | التفعيل قرار منفصل بصلاحية محددة |
| إدارة المديرين للمدير الرئيسي فقط، مع بقاء مدير رئيسي نشط واحد على الأقل | منع تصعيد الصلاحيات وفقدان الإدارة |

## المرحلة 2: الكشوف والمواطنون والدورات

### دورة حياة الكشف

```
رفع الملف ─► حفظ الملف الأصلي ─► استخراج جدول خام ─► ربط الأعمدة ─► صفوف + تحقق
                                                                          │
                     (قيد المراجعة: تصحيح، استبعاد، تغيير الربط، تحديد الدورة)
                                                                          │
                                        اعتماد صريح ──► مواطنون + استحقاقات
                                        أو إلغاء (يبقى محفوظًا)
```

- **الاستخراج:** Excel (‎.xlsx) عبر ExcelJS؛ PDF نصي عبر pdf.js (مكتبة unpdf) مع تجميع الكلمات في صفوف وأعمدة حسب مواضعها؛ PDF ممسوح ضوئيًا يُقرأ **في متصفح الموزّع** (pdf.js + tesseract.js) وتُرسل الكلمات ومواضعها فقط إلى الخادم.
- **ربط الأعمدة:** يُكتشف تلقائيًا من كلمات العناوين (أو من المحتوى عند غيابها)، ويمكن للموزّع تعديله في شاشة المراجعة. الجدول الخام محفوظ، فإعادة الربط لا تحتاج إعادة رفع.
- **التحقق:** رقم الهوية (9 أرقام ورقم تحقق Luhn)، الاسم، رقم المواطن، عدد الجرار، التكرار داخل الكشف، استحقاق قائم للمواطن في كشف آخر بالدورة، رقم مواطن مستخدم، اختلاف الاسم عن المسجل، اختلاف المبلغ عن (العدد × السعر). الأخطاء تمنع الاعتماد؛ التنبيهات لا تمنعه.
- **صفوف القراءة الضوئية** تُعلَّم كلها «تحتاج مراجعة». رقم التحقق في الهوية يكشف معظم أخطاء القراءة تلقائيًا.
- **الاعتماد:** في معاملة واحدة مع قفل الكشف والدورة (`SELECT … FOR UPDATE`)، فلا يتكرر حتى مع طلبات متزامنة.
- **الإصدارات:** الكشف الجديد يمكن أن «يحل محل» كشف معتمد. قبل الاعتماد تُعرض الفروق (جدد، تغيّرت بياناتهم، اختفوا). عند الاعتماد: يصبح السابق «إصدار سابق» ويبقى بصفوفه وملفه؛ تُسجل كل تغييرات الاستحقاق في `entitlement_changes`؛ المختفون يُعلَّم استحقاقهم «أُزيل» ولا يُحذف.

### المواطنون والاستحقاقات

- **المواطن لا يُنشأ إلا من كشف معتمد.** لا توجد أي واجهة لإنشاء مواطن أو استحقاق يدويًا؛ المواطن غير الموجود يُسجل «حالة مراجعة» فقط.
- **بيانات الهيئة منفصلة:** الاستحقاق يحفظ ما ورد في الكشف المعتمد (الاسم، الهاتف، رقم المواطن، الكمية، المبلغ ومصدره، السعر والعملة وقت الاعتماد). عمليات الموزّع (المراحل 3 و4) في جداول مستقلة.
- **المبلغ المطلوب (قرار مؤقت):** مبلغ الكشف إن ورد، وإلا عدد الجرار × سعر الدورة. يُحفظ مصدره، ويُنبَّه عند اختلاف الاثنين.
- **رقم المواطن** هو معرّف الجرة التشغيلي **داخل الدورة**: فريد بين الاستحقاقات القائمة في الدورة نفسها (قيد في قاعدة البيانات)، وقد يتكرر بين الدورات.
- **الدمج:** اقتراحات بأسماء متشابهة (≥ 85٪) وأرقام هوية مختلفة؛ قرار بشري فقط؛ يُرفض إن كان للسجلين استحقاق قائم في الدورة نفسها؛ لا تُجمع الكميات؛ السجل الثانوي يبقى مربوطًا بالأساسي، والبحث برقمه يوصل للأساسي.
- **تشابه الأسماء يُحسب في الكود** لا بـ pg_trgm، لأن الأخير يتجاهل الحروف العربية في بعض إعدادات لغة قاعدة البيانات.

### الحماية في قاعدة البيانات (ترحيلات phase2)

| الحماية | كيف |
|---|---|
| عزل كل جداول المرحلة | سياسة RLS على 11 جدولًا |
| منع ربط سجل موزّع بسجل موزّع آخر | مفاتيح خارجية مركّبة `(id, distributorId)`، لأن فحص المفاتيح لا يخضع لـ RLS |
| دورة نشطة واحدة | فهرس فريد جزئي `WHERE status = 'OPEN'` |
| استحقاق قائم واحد لكل مواطن في الدورة | فهرس فريد جزئي |
| رقم مواطن فريد في الدورة | فهرس فريد جزئي |
| لا حذف للبيانات من التطبيق | سحب صلاحية `DELETE` من دور التطبيق على كل الجداول، عدا التصنيفات وصفوف كشف قيد المراجعة |
| صفوف الكشف المعتمد ثابتة | trigger يمنع أي تعديل أو حذف لصفوف كشف ليس قيد المراجعة |
| سجلات ثابتة | `cycle_events` و `entitlement_changes` و `file_blobs` للإضافة فقط |

### تخزين الملفات (مؤقت)

الملفات الأصلية تُحفظ في PostgreSQL (`file_blobs`) خلف واجهة `storeFile/readOwnFile`، إلى حين اعتماد مزوّد تخزين سحابي. الميزة الحالية: الملفات مشمولة في نسخ قاعدة البيانات الاحتياطية. القيد: حجم القاعدة يكبر مع الملفات (الحد 20 ميغابايت للملف). صور الهويات **لا تُرفع ولا تُخزن إطلاقًا**؛ تُقرأ على الجهاز.

## المرحلة 3: الجرار والمخزون والشحنات

### نموذج الجرة

```
(استحقاق بعدد n) ─ استلام فارغة ─► جرة EMPTY ─ تعبئة (داخلية أو ضمن شحنة) ─► FILLED ─ تسليم ─► DELIVERED
                                       │                                         │                  │
                                       └──────────── إلغاء آخر عملية يعيد الحالة السابقة (VOID ◄ EMPTY ◄ FILLED)
```

- **كل جرة سجل مستقل.** رقمها رقم المواطن في الكشف («501»)، ومع تعدد الجرار «501-1» و«501-2». الرقم فريد داخل الدورة بين الجرار غير الملغاة.
- **العملية** (استلام، تعبئة، تسليم) سجل في `cylinder_operations`. القيد الجزئي `(cylinderId, type) WHERE status = 'ACTIVE'` يجعل قاعدة البيانات نفسها تمنع تعبئة الجرة مرتين أو تسليمها مرتين.
- **منع التكرار عند إعادة الإرسال:** معرّف عملية من الجهاز فريد لكل موزّع. يُفحص قبل التنفيذ ثم **بعد الحصول على قفل الصف**. الطلب المكرر المتزامن ينتظر القفل، ثم يرجع نتيجة الأول بدل أن يرجع خطأ.
- **الهوية:** رقم البطاقة المدخل يجب أن يطابق صاحب الاستحقاق، ولا يوجد أي مسار تجاوز. عدم المطابقة يوقف العملية ويسجل حالة مراجعة في معاملة مستقلة.
- **الدورة المغلقة:** لا يُستلم فيها فارغ جديد، لكن الجرار المعلقة تُعبأ وتُسلّم لأصحابها.
- **الاستحقاق المُزال بإصدار جديد:** جراره المستلمة تبقى قابلة للتعبئة والتسليم، ولا يُستلم له جديد. الإصدار الذي يغيّر رقم مواطن له جرار مستلمة، أو يُنقص العدد تحته، يُرفض في المراجعة.
- **العمليات لا تمس المال:** لا عملية جرار تغيّر مبلغًا. الدفع عملية مالية منفصلة (المرحلة 4).

### المخزون

| الحركة | فارغ | معبأ (جرار مواطنين) | إضافي (من الشحنات) |
|---|---|---|---|
| استلام فارغة | +1 | | |
| تعبئة (داخلية أو ضمن شحنة) | −1 | +1 | |
| تسليم | | −1 | |
| شحنة: الكمية غير المرتبطة بمواطنين | | | +n |
| إلغاء | عكس الحركة الأصلية مرة واحدة (`reversesId` فريد) | | |

- **الشحنة لا تضاعف المخزون:** الجزء المرتبط بمواطنين يُسجل **تعبئةً** لجرار مستلمة فارغة (حركة FILL لكل جرة، مع مرجع الشحنة)، والباقي حركة `SHIPMENT_EXTRA` مستقلة. الجرة الواحدة لا تُعبأ إلا مرة.
- **الرصيد** في `inventory_balances` يُحدَّث ذريًا مع كل حركة (`UPDATE … RETURNING` يقفل الصف). قيد في قاعدة البيانات يمنع أي رصيد سالب، فالحركة غير المنطقية تُرفض. كل حركة تحفظ الرصيد بعدها.
- **المطابقة:** الرصيد يُقارن دائمًا بحالات الجرار الفعلية وبالكميات الإضافية للشحنات النافذة. أي اختلاف يظهر تنبيهًا ولا يُصحح تلقائيًا.

## المرحلة 4: المالية

### الفصل بين المجالات

| المجال | السجل | يؤثر في |
|---|---|---|
| تحصيلات المواطنين | `payments` (مرتبطة باستحقاق دورة) | متبقي المواطن، ومقبوضات الصندوق |
| المصروفات | `expenses` | مدفوعات الصندوق |
| حسابات المحطات | `shipments` (القيمة = العدد × سعر الشراء) و `station_payments` | رصيد المحطة؛ ودفعاتها مدفوعات من الصندوق |
| الجرار والمخزون | المرحلة 3 | لا تمس أي مبلغ |

- **سعران مختلفان:** سعر البيع للمواطن تحدده الهيئة (سعر الدورة، محفوظ في كل استحقاق). سعر الشراء من المحطة يُقترح من سعر المحطة الافتراضي ويُحفظ **في كل شحنة**، فتغيير أي منهما لاحقًا لا يغيّر الحسابات السابقة.
- **العملة:** كل سجل مالي يحفظ عملته وقت إنشائه. التحصيل يأخذ عملة الاستحقاق، والمصروفات ودفعات المحطات تأخذ عملة الإعدادات وقتها.
- **الصندوق** يحسب: المقبوضات − المصروفات − دفعات المحطات. لا فتح ولا إغلاق يومي. **الرصيد محسوب ولا يثبت النقد الفعلي.** التصفية بالدورة تعني: التحصيلات المرتبطة بالدورة، والمصروفات ودفعات المحطات خلال فترتها (من الفتح إلى الإغلاق أو الآن).
- **الاستحقاق القابل للتحصيل:** القائم في الكشف، أو المُزال الذي استُلمت له جرار.

### الحماية في قاعدة البيانات

| الحماية | كيف |
|---|---|
| لا دفع زائد | trigger قبل الإدراج يقفل صف الاستحقاق ويرفض أي دفعة تجعل المدفوع أكبر من المطلوب، إضافة إلى الفحص في الكود |
| لا خفض للمطلوب تحت المدفوع | trigger على `entitlements.amountDue` يحمي من تعديل يدوي أو إصدار كشف جديد |
| السجلات لا تُعدّل ولا تُحذف | trigger `app_cancel_only` على التحصيلات والمصروفات ودفعات المحطات والشحنات وعمليات الجرار: التغيير الوحيد المسموح ACTIVE ← CANCELLED مع حقول الإلغاء، مرة واحدة |
| مبالغ موجبة | قيود CHECK |
| العزل | RLS ومفاتيح مركّبة كبقية الجداول |

### تحذير للترحيلات المستقبلية

`prisma migrate diff` لا يعرف القيود والفهارس والـ triggers المكتوبة يدويًا، **ويقترح حذفها**. عند توليد ترحيل جديد يجب حذف أي سطر `DROP CONSTRAINT` أو `DROP INDEX` يخصها. الاختبار `tests/integration/schema-guards.test.ts` يفشل إن حُذف أي منها.
