# البنية والقرارات التقنية

## نظرة عامة

```
src/
  app/                 صفحات Next.js وواجهات API
    (app)/admin/...    صفحات مديري النظام
    (app)/d            صفحات الموزّع
    (app)/account      حسابي (كلمة المرور، PIN، الأجهزة)
    api/v1/...         واجهات JSON (موثقة في docs/api.md)
  server/              منطق الخادم فقط (لا يُستورد في المتصفح)
    db.ts              الاتصال وسياقات العزل withTenant / withSystem
    actor.ts           هوية المنفذ والتحقق من الصلاحيات
    permissions.ts     صلاحيات مديري النظام
    audit.ts           كتابة سجل التدقيق
    auth/              كلمات المرور، الجلسات، PIN
    services/          خدمات الأعمال (الموزّعون، المديرون، الإعدادات، السجلات، التصدير)
    http/              حراس الصفحات وAPI، معالجة الأخطاء، CSRF
  components/          مكونات الواجهة
  lib/                 أدوات مشتركة (تنسيق التواريخ، القائمة)
prisma/
  schema.prisma        مخطط البيانات
  migrations/          ترحيلات SQL (منها ترحيل الحماية: RLS والـ triggers)
scripts/               سكربتات التشغيل والإعداد
tests/                 اختبارات الوحدات والتكامل
```

**القاعدة:** كل عملية تمر عبر خدمة في `src/server/services`، تستقبل `Actor` الذي بناه الخادم من الجلسة، وتتحقق من الصلاحية بنفسها. واجهات API والصفحات طبقة رقيقة فوق الخدمات. لا تُبنى الهوية أبدًا من بيانات يرسلها العميل.

## عزل بيانات الموزّعين (طبقتان)

1. **طبقة التطبيق:** خدمات الموزّع تستخدم `withTenant(actor.distributorId, ...)`، وخدمات الإدارة تتحقق من دور المدير وصلاحيته قبل استخدام `withSystem`.
2. **طبقة قاعدة البيانات (Row-Level Security):**
   - التطبيق يتصل بالدور `gas_app` (ليس مالك الجداول ولا يملك `BYPASSRLS`)، فتُطبق عليه سياسات RLS دائمًا.
   - كل معاملة تحدد سياقها بـ `set_config(..., true)` (محلي للمعاملة فقط):
     - `app.distributor_id`: سياق موزّع واحد.
     - `app.bypass_rls = on`: السياق المركزي (المديرون، المصادقة).
   - **فشل مغلق:** أي استعلام خارج السياقين لا يرى أي صف من الجداول المعزولة.
   - الجداول المعزولة حاليًا: `distributors` و `users` و `audit_logs`. كل جدول بيانات تشغيلية في المراحل القادمة (كشوف، مواطنون، دورات، عمليات، مخزون، مالية) سيحمل `distributorId` وسياسة RLS نفسها.

اختبارات `tests/integration/isolation.test.ts` تتحقق من ذلك على قاعدة PostgreSQL حقيقية.

## المصادقة والجلسات

- كلمات المرور وPIN مجزأة بـ **Argon2id** (معاملات OWASP: 19 MiB، تكراران).
- الجلسة رمز عشوائي (256 بت) في ملف تعريف ارتباط `HttpOnly` و `SameSite=Lax` و `Secure` في الإنتاج. قاعدة البيانات تخزن **تجزئة SHA-256** للرمز فقط.
- يُتحقق من كل طلب على الخادم: الإبطال، مهلة عدم النشاط (من الإعدادات)، العمر الأقصى (7 أيام)، حالة المستخدم، حالة الموزّع وصلاحيته.
- **قفل الحساب** بعد عدد المحاولات الفاشلة المحدد في الإعدادات، مع حد إضافي للمحاولات الفاشلة من عنوان IP واحد (50 خلال 15 دقيقة).
- رسالة الفشل موحدة لكلمة مرور خاطئة ولمستخدم غير موجود، مع تحقق وهمي بزمن مماثل حتى لا يُكشف وجود الحساب.
- كل محاولة دخول (ناجحة أو فاشلة) تُسجل مع الوقت وعنوان IP في `login_attempts` (للإضافة فقط).
- **PIN:** مرتبط بجهاز واحد عبر رمز جهاز في ملف تعريف ارتباط `HttpOnly` و `SameSite=Strict`. تفعيله يتطلب كلمة المرور، ويُلغى بعد 5 محاولات خاطئة. جلسة PIN **لا تكفي للعمليات الحساسة**.
- **العمليات الحساسة** (إعادة تعيين كلمات المرور، إدارة المديرين، الخروج من كل الأجهزة) تتطلب تحققًا بكلمة المرور خلال آخر 15 دقيقة. الواجهة تطلبه تلقائيًا ثم تعيد المحاولة.
- **نسيان كلمة المرور:** يعيد المدير تعيينها بعد التحقق من الهوية، مع إلزام بتسجيل السبب وطريقة التحقق، وإلزام الموزّع بتغييرها عند الدخول، وإبطال الجلسات وPIN افتراضيًا.
- **CSRF:** كل طلب معدِّل يجب أن يحمل `Origin` مطابقًا للمضيف، إضافة إلى `SameSite`.

## دورة حياة حساب الموزّع

| الحالة | الدخول | ملاحظات |
|---|---|---|
| نشط `ACTIVE` | مسموح | قد يكون تجريبيًا أو فعليًا، بتاريخ انتهاء أو بلا مدة |
| معلّق `SUSPENDED/MANUAL` | ممنوع | قرار إداري مع سبب |
| منتهي `SUSPENDED/EXPIRED` | ممنوع | تعليق تلقائي عند انتهاء الصلاحية |
| مؤرشف `ARCHIVED` | ممنوع | مخفي من القائمة الافتراضية؛ لا تُحذف أي بيانات |

**التعليق التلقائي:** يُنفذ عند كل تحقق من جلسة، وعند كل محاولة دخول، وعند عرض قوائم الإدارة. لا يمكن لحساب منتهٍ تنفيذ أي عملية حتى دون مهمة مجدولة. التحديث شرطي (`WHERE status = 'ACTIVE'`) فلا يتكرر السجل عند تزامن طلبين.

التعليق والأرشفة يبطلان كل جلسات الموزّع فورًا.

## سجل التدقيق

- يُكتب **داخل المعاملة نفسها** مع العملية، فلا تُعتمد عملية دون سجلها.
- يحفظ القيم القبلية والبعدية والسبب والمنفذ وعنوان IP. يحذف تلقائيًا أي حقل سري (`passwordHash` و `pinHash` وغيرهما).
- **محمي من التعديل** على مستويين:
  - `gas_app` لا يملك صلاحيات `UPDATE` و `DELETE` و `TRUNCATE` على الجدول.
  - Triggers تمنع التعديل والحذف والتفريغ حتى لمالك قاعدة البيانات.
- المبدأ نفسه مطبق على `login_attempts` و `error_logs`.

## الأخطاء التقنية

كل خطأ غير متوقع في API يُسجل في `error_logs` (الرسالة، المسار، المستخدم)، ويرجع للعميل رسالة عامة دون تفاصيل داخلية. الإشعار الداخلي لمدير النظام عند الأخطاء المهمة يُضاف مع نظام الإشعارات (المرحلة 7).

## القرارات التقنية والافتراضات

| القرار | السبب |
|---|---|
| Prisma مع ترحيلات `migrate` (لا `db push`) | تاريخ تغييرات قابل للمراجعة، ولا حذف بيانات صامت في الإنتاج |
| RLS في PostgreSQL مع دور تطبيق منفصل | عزل لا يعتمد على تذكّر كل مطور إضافة شرط الموزّع |
| جلسات في قاعدة البيانات بدل JWT | إمكانية الإبطال الفوري (تعليق، خروج من كل الأجهزة، مهلة عدم النشاط) |
| واجهات `/api/v1` بدل Server Actions | API موثقة قابلة للتوسع، وأساس للمزامنة دون اتصال (المرحلة 6) |
| التواريخ بتوقيت `Asia/Gaza` وبصيغة يوم/شهر/سنة بأرقام لاتينية | وضوح التواريخ داخل نص عربي |
| إعدادات العملة لا تغيّر العمليات السابقة | كل عملية مالية (المرحلة 4) ستخزن عملتها وقيمتها وقت التنفيذ |
| إعادة الحساب من الأرشيف تعيده «معلّقًا» | التفعيل قرار منفصل بصلاحية محددة |
| إدارة المديرين للمدير الرئيسي فقط، مع بقاء مدير رئيسي نشط واحد على الأقل | منع تصعيد الصلاحيات وفقدان الإدارة |

## قيود معروفة في هذه المرحلة

- رفع الشعار ينتظر اعتماد مزوّد التخزين السحابي.
- تخصيص أسماء الأقسام وترتيبها، وإعدادات أنواع الملفات وأحجامها، مجدولة في المرحلة 5.
- عرض الجلسات النشطة لكل جهاز بالتفصيل غير متوفر؛ يتوفر عددها وإنهاؤها جميعًا.
